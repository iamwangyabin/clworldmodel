我们究竟站在哪里

不是罗列论文，而是逐条检查已有路线已经保护了什么、默认了什么、以及它们为何还不能回答 Dreamer 在持续学习里究竟忘了哪个模块。

范围：continual / multi-task MBRL 核心对象：World Model + Actor-Critic 协议：task-agnostic 为主 结论：当前问题仍未被闭合

阅读结论

现有工作大致分成五类：保留真实经验、维护预测模型、直接保护行为、用条件结构处理多任务冲突、 以及把视觉表征从在线强化学习中剥离。每类都解决了真实问题，但它们通常把“性能下降”整体当作一个问题。 对 Dreamer-style agent 而言，世界模型、价值估计与 Actor 的训练信号不同，不能因为都在 replay 上训练就默认它们 遗忘相同，也不能因为某一论文中 world model 稳定就把它当成普遍定律。

R2

Dreamer family

Dreamer 给了什么，也留下了什么

R2.1 DreamerV3：世界模型不是策略本身

DreamerV3 将真实经验压缩为 latent state，学习 reward 与 continuation，并在 imagined rollout 中训练 Actor-Critic。 它证明了统一世界模型可在大量域中使用固定超参数，但它研究的是跨域鲁棒性，不是顺序任务下旧技能的保持。 因而它不能回答：一个训练良好的 RSSM 发生轻微漂移时，Actor 是否还能使用它完成旧游戏。 [DreamerV3]

R2.2 Continual-Dreamer：选择 replay 的关键基线

Continual-Dreamer 系统比较了多种 selective experience replay，并明确讨论了 retention、transfer 和 exploration。 它是“世界模型天然适合 continual learning”这条路线最重要的早期证据。可它仍主要以任务回报判断方案， 没有将同一次性能下降拆成 WM、Critic 与 Actor 的可干预贡献。因此它告诉我们“什么 replay 在一些基准上有效”， 却没有告诉我们“为什么本次掉分，以及应该保护谁”。[Continual-Dreamer]

R2.3 Online world-model planning：理论上的“不忘”不等于 Dreamer 不忘

Online world-model planning 通过在线学习与规划器给出特定假设下的 regret/forgetting 保证。这类结论针对浅层、 显式规划的模型与其协议；它不自动转移到高维像素、神经 RSSM、想象策略梯度或固定 replay 的 Dreamer。 所以它是重要的理论参照，而不是对“Dreamer 世界模型本质不会忘”的证明。[Online World Models]

对本项目的含义：Continual-Dreamer 是 replay 设计上的强先例；但“world model 有 replay”与 “old policy 能控制”之间仍隔着 Critic、imagination distribution 与 Actor optimization 三层机制。
R3

Replay and memory

经验回放解决覆盖，不自动解决归因

R3.1 从监督持续学习到持续强化学习

在分类持续学习中，reservoir sampling、herding、coreset 和优先级方法回答的是：在固定 memory 下， 哪些样本最能近似历史数据分布或决策边界。迁移到 RL 后，样本不再是静态 (x, y)；一段轨迹同时承担 视觉、动力学、reward、termination、value bootstrap 与行为学习的监督。一个“代表样本”对 Encoder 可能足够， 对稀有决策状态却可能完全不够。

R3.2 CLEAR 与 RECALL：直接回放行为，但有自己的前提

CLEAR 将 off-policy replay 与 behavioral cloning 结合，明确把旧策略的动作分布作为巩固目标；RECALL 则探索 生成式 replay 增强持续 RL。两者提醒我们，旧技能不该只靠重新做 RL “碰巧学回来”。但它们多在 model-free 设定讨论，不能回答 dream state 是否可信、Actor 应在真实轨迹还是想象轨迹上巩固，以及 value target 如何处理。 [CLEAR] [RECALL]

R3.3 ARROW：双 buffer 的贡献与边界

ARROW 将固定轨迹预算分为 FIFO 与长期分布匹配记忆，在不显式给模型 task ID 的前提下，同时维持当前适应与历史覆盖。 它的创新在 retention distribution，而不是在 Dreamer 模块的更新规则。尤其在我们自己的 6-task Atari pilot 中，Frostbite/Boxing 的保持较好，CrazyClimber/Seaquest 更脆弱，说明同一个 buffer 机制对不同任务并不等价。 这不能证明 ARROW 失败，但足够说明“有历史轨迹”不是完整诊断。[ARROW]

记忆策略近似保持什么在 Dreamer 里缺少什么我们应做的匹配控制
FIFO当前分布密度历史覆盖随任务数稀释固定总 trajectory / byte 预算
Reservoir / LTDM历史流的无偏覆盖不识别控制关键状态同容量、同采样比的随机控制
Herding / coreset表示空间代表性表征会漂移；代表性未必是 reward-relevant冻结 encoder 与在线 encoder 两种协议
Priority / value-aware高 TD error 或高价值状态Critic 非平稳会让选择偏置自我强化匹配 sample count 与更新次数
行为克隆 target旧策略技能保留旧行为不代表它仍最优真实回放与 graded dream 分开消融
R4

Actor, critic, and dreams

“Actor 忘了”是强假设，不是默认事实

R4.1 Dream rehearsal 的关键发现

The World Model Remembers, the Actor Forgets 在它的 never-clear replay 协议下做了组件级 probe： 旧任务的 reward discrimination、value 与 termination 可以保持，而 Actor 行为坍塌；在相同冻结 world model 上继续 imagined RL 不能恢复技能，但从经过评分的 dreams 做自模仿可以。这是目前与我们问题最直接的工作， 因为它不是只报告 return，而是干预模块。[Dream Rehearsal]

R4.2 为什么不能直接把它当作结论

该结论依赖其环境、模型、replay 语义、评估与 grading 机制。ARROW 的 finite FIFO/LTDM、不同 Atari 动力学、 像素重建、reward scale 和训练日程都可能改变瓶颈。即使世界模型在一些指标上稳定，也不代表长 horizon latent rollout 对旧策略没有 control-relevant error。反过来，Actor 看似忘记也可能来自 Critic 校准漂移或 imagined state distribution 改变。它给了我们一个可检验的竞争假设，不是要我们跳过诊断直接做 imitation。

R4.3 本项目的必要复现实验

  1. 在每个任务边界保存 WM、Actor、Critic 和 replay provenance。
  2. 在旧真实环境上测新旧组件交叉组合，而非只看最终单个 agent。
  3. 固定旧 Actor，替换新/旧 WM；固定 WM，替换新/旧 Actor；再单独替换 Critic。
  4. 比较 real-episode cloning、ungraded dream、graded dream 和无 Actor 保护，所有方法匹配字节、updates 和参数。
对本项目的含义：若 ARROW 上也出现“WM 稳定、Actor 失效”，Actor rehearsal 才是主线；若 RSSM/reward/continue 或 critic 已先坏，直接蒸馏 Actor 只能是补丁。
R5

Multi-task and modularity

MoE 不是创新点，它只是一个容量工具

多任务 RL 已经长期处理负迁移、梯度冲突与容量共享。PCGrad 在梯度层面减少冲突；Soft Modularization、CARE 与 PaCo 通过条件模块或参数组合决定共享方式；MoW 把这一思想扩展到视觉 world model，并使用任务条件专家与梯度聚类。 这些工作说明“共享骨干 + 专用容量”是合理工程方向，但它们的大多数训练设定是并行/联合多任务，或拥有任务 metadata。

路线解决的真实难点与持续 Dreamer 的错位对我们的约束
PCGrad并行任务的梯度冲突顺序任务下旧梯度只来自有限 replay不能以“减少冲突”替代 retention 测试
CARE用 context 选择状态表征，缓解负迁移默认可用任务相关 metadatatask ID 只能作为 oracle 上界，不可作为最终输入
Soft Modules / PaCo模块路由或策略参数组合主要保护 policy capacity，不定位 world model / critic需匹配参数、激活 FLOPs 与任务标签信息
MoW视觉压缩与动力学模块化联合 26 task，不是顺序有限回放遗忘协议先做 shared RSSM 与 oracle/context routing 上界

因而“给 RSSM 加 MoE”本身没有足够新意。能成立的研究问题是：在没有 task ID、历史数据有限的顺序训练中， 路由依据能否由 control-relevant prediction error 或 value consequence 给出，并且这种路由是否真的 减少了被组件干预确认的遗忘，而不是仅把任务分类到不同专家。

代表来源：[CARE] [PaCo] [MoW]

R6

Representation and prediction target

视觉编码器可不可以退出持续学习？

R6.1 这不是细枝末节，而是协议分叉

DreamerV3/ARROW 从 64×64 像素训练 Encoder 和 decoder，并使用重建项。DINO-WM 则在预训练视觉特征上学习动作条件预测， 不重建像素；MuDreamer 进一步表明 Dreamer-style world model 可用价值和动作等预测目标避免像素重建。它们共同动摇了一个默认： 为了学控制相关 dynamics，必须持续更新像素 encoder/decoder。[DINO-WM] [MuDreamer]

R6.2 但不能偷换成“冻结 encoder 一定更好”

DINO-WM 的目标是预训练视觉特征上的规划，MuDreamer 的目标是鲁棒预测学习；两者都不等同于顺序 Atari 中的 Dreamer actor-critic。 固定 encoder 可能显著减少存储和稳定性压力，也可能丢掉游戏中 reward-critical 的细节。更重要的是，一旦我们冻结 encoder， 研究问题就从“端到端世界模型抗遗忘”变成“固定视觉表征上的持续动力学与控制”。这是合理、甚至更干净的协议， 但必须明确命名，并和端到端 ARROW 公平比较。

方案应保留什么省掉什么新增风险
端到端 Dreamer / ARROWraw o,a,r,c无额外预训练假设视觉、解码、dynamics、Actor 同时漂移；replay 大
冻结 encoder，存 latent featurefeature,a,r,c，且须记 encoder version不必存 raw pixel；不更新视觉 backbonefeature 对 reward/dynamics 可能不充分；公平性协议改变
预测而非重建control-relevant target像素 decoder 与多数重建损失target 选择不当会遗漏可控变量
对本项目的含义：冻结视觉编码器不是“优化小技巧”，而是一个强且值得单独研究的假设。 它可以成为低存储协议的基线，但不可悄悄替换 ARROW 的端到端设定后仍称为公平比较。
R7

Project position

我们目前真正的研究空缺

目前不能声称“第一个解决持续世界模型遗忘”，也不能声称“第一个让 Actor 不忘”。已有工作已经分别研究了 replay、 selective memory、dream rehearsal、条件专家和无重建世界模型。我们可成立的空间更窄，也更扎实：

在固定资源、task-agnostic、顺序任务的 Dreamer-style agent 中，先用可干预组件诊断确定旧回报下降的因果来源； 再只对被确认的目标设计 memory、rehearsal 或条件容量，并同时报告轨迹容量、实际字节、更新次数、参数与计算量。

已有观察不能直接推出必须补的证据可能的后续方法
ARROW pilot 的保持率任务异质、非单调某一个模块一定是瓶颈WM / Actor / Critic 交叉置换诊断优先，不先押 MoE
Dream rehearsal 在另一协议中发现 Actor 是瓶颈ARROW 上 Actor 一定是瓶颈同协议复现 probe；真实与 dream rehearsal 对照graded dream 或 policy distillation
MoW 等多任务方法能用模块化扩容条件专家本身就是创新oracle/context/value-aware routing 消融control-aware conditional RSSM
DINO-WM / MuDreamer 弱化像素重建必要性冻结 encoder 对 Atari CL 无损端到端 / frozen feature 同预算比较feature replay 与持续 dynamics
论文叙事的止损线。 如果组件诊断显示统一 ARROW replay 已能同时保持 WM、Critic 和 Actor，那么不应硬写“双类记忆”或 MoE； 应转向更小 memory、更多任务或更严格的 byte budget。反之，只有某类故障跨 seed 稳定出现，结构方法才有必要。
